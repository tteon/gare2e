Where a GraphCoT second goes: decode owns 82–98 % of the wall at every query class and every concurrency we can buy

Before optimising anything, the talk needs an honest baseline: for one request, which layer — graph database, agent orchestration, vLLM host side, GPU prefill, GPU decode — holds the wall, per reasoning turn and per query class. This page reads that off two paid sessions over the same 360 B0 cases (strata-v2, 30 per class per lane): lab-s11 at K=4 and K=8, lab-s12 at K=16 and K=32, plus an async-scheduling off pass and a result-size pass. Reasoning off, Qwen3.6-27B, TP=2.

lab-s11: 2× RTX PRO 6000 PCIe pair, $2.66/h, 140 min lab-s12: 2× A100 SXM4 NVLink NV12, $2.30/h, 170 min spend $6.2 + $6.5 (+ $2.05 on two aborted starts) query classes L1 / L2 / L3 = easy / medium / hard (structural rubric)

Terminology. The agents measured here run an iterative Text2Cypher / Text2SPARQL loop in the GraphCoT style: each turn thinks, calls inspect_graph_schema or a whole-query tool (execute_cypher / execute_sparql), observes the result and continues, up to six turns. They are not the original Graph-CoT action set (RetrieveNode / NodeFeature / NeighbourCheck / NodeDegree, hop by hop); that lane is being added as lab 017 for a direct comparison.

3 · The CPU hypothesis, tested

What we expected to see

If host-side work (tokenisation, scheduling, detokenisation, tool-call parsing, prompt reconstruction) were the bottleneck, GPU utilisation would fall while the host CPUs saturate, the tool-use gap between turns would grow with K, and queue time per request would climb.

What the samples show

GPU utilisation does fall (93 → 66 %), but vLLM's host processes use a flat ≈ 3.0 cores at every K on 32- and 128-core hosts, the agents 0.3 → 1.6 cores, DozerDB ≤ 0.1. Queue is 0.002 → 0.067 s per request. The tool-use gap residual (gap − graph call) is 0 ms at p90 in every stratum and every K.

Reading

The GPU idles at high K because decode is memory-bound at small batches (KV ≤ 14 %) and because agents leave the batch during tool calls, not because the CPU cannot feed it. One open point: three flat cores can be three saturated single threads or three polling loops; a per-process breakdown (API server / engine core / worker) is the next observability item.

Where contention did appear

DozerDB. GRBench single graph calls: p50/p90 16/35 ms at K=4, 38/99 ms at K=16, 7/48 ms at K=32; calls reaching the 15 s bound 3 → 9 → 8 per pass. The timeout holds, but under 16–32 concurrent agents the database, not the host, is the first shared resource to show a tail.

5 · Decode ratio, defined and measured

Decode ratio (per request) = T_decode / T_inference → p50 0.90 – 0.96, every lane, class and K Decode E2E ratio (per case) = Σ T_decode / GraphCoT E2E wall → p50 0.84 – 0.95 single lanes, 0.98 multi lanes

Both ratios are computed from the vLLM server spans (queue, prefill, decode per request) joined to the case receipts; no prompts or answers are read. The stat the talk wanted — "in L3 decode dominates" — is true, but so is "in L1 decode dominates": the class shifts turns and tokens, not the layer mix.

6 · Two smaller axes

  • Async scheduling (vLLM 0.27.1, on by default). Forcing --no-async-scheduling at K=16: −4.5 % tok/s, +7 % ITL, +7–10 % per-case wall, funnel unchanged. Keep the default; no reason to make it an experiment axis.
  • Result size (row cap 20 → 100, byte cap 12 k → 60 k; medium stratum, K=4). GRBench single validated 30/30, non-empty 30/30 in both; answered 17 vs 16; wall 9.9 vs 8.9 s; output tokens 371 vs 428; no timeouts. The cap is never binding at this cohort's result sizes — result size is not a lever here.
  • Funnel invariance. Across K = 4/8/16/32 and async on/off every funnel column moves ≤ 3 cases per 30-case cell. Serving shape changes time and energy; it does not change what the agent does.

7 · What Experiment 0 settles for the talk

  • The three-layer trace (task / pipeline / system) joined by trace id and turn exists and is validated at 99 % request coverage; every table on this page comes from it without reading prompts or answers.
  • "GraphCoT is decode-heavy" is measured, not assumed: 0.82–0.98 of the wall in every cell. Speculative decoding is the right lever in principle — but the lane's own parity test (lab-s4/s7: greedy Cypher changed, validated 100 → 50 %) means any speculative result must be reported with query-correctness alongside speed.
  • The heterogeneous-pipeline story (CPU / host orchestration as a hidden 30 %) does not hold on this stack at K ≤ 32. Host + agent together stay under 10 %. The second shared resource that shows contention is the graph database, and only from K=16.
  • Concurrency is a throughput knob with a linear latency price and no effect on behaviour. For the serving story: one TP=2 engine, K=4 for interactive latency, K=8–16 for batch; K=32 only if latency does not matter.
  • Open observability items (lab 011): per-process CPU split for vLLM (API server / engine / worker), DB server-side stage attributes, and the runner service.name fix validated live (it is: lab-s12 client spans read seocho-agentic-os).
