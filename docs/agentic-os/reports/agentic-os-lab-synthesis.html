그래프 위에서 추론하는 에이전트를 열흘 동안 계측한 결과: 무엇을 재고, 무엇을 알았고, 무엇을 아직 모르는가

이 문서는 lab-s3부터 lab-s13까지 11개의 유료 세션(누계 약 $78)과 그 사이의 코드 작업을, 처음 읽는 사람도 따라올 수 있게 한 번에 정리한 것입니다. 먼저 실험 장치와 용어를 풀고, 세션이 각각 어떤 질문에 답했는지, 그래서 지금 확실한 것과 여전히 열린 것을 구분합니다. 숫자는 모두 리포트와 receipt에서 그대로 가져왔습니다.

모델 Qwen3.6-27B (TP=2, reasoning off) 서빙 vLLM 0.27.1 그래프 DozerDB(Cypher) · Oxigraph(SPARQL) 인프라 Vast.ai 2-GPU 어플라이언스, 세션당 1–3시간

용어. 여기서 측정한 에이전트는 GraphCoT 형태의 반복 Text2Cypher / Text2SPARQL 루프입니다: 매 turn 생각하고, 스키마 도구 또는 질의 전체를 실행하는 도구(execute_cypher / execute_sparql)를 부르고, 결과를 보고 다음 turn으로 갑니다(최대 6 turn). 원 논문 Graph-CoT의 hop 단위 행동(RetrieveNode / NodeFeature / NeighbourCheck / NodeDegree)은 아닙니다. 그 lane은 lab 017로 추가해 직접 비교합니다.

0 · 한 문단 요약

우리는 "질문 → 스키마 확인 → 그래프 질의 생성 → 실행 → 결과 보고 다음 생각" 을 반복하는 GraphCoT 에이전트를, 두 개의 공개 벤치마크 위에서, 요청 한 건·추론 turn 한 번 단위로 계측하는 장치를 만들었습니다. 그 장치로 확인한 것은 네 가지입니다. (1) 시간의 82–98%는 GPU decode이고, CPU·오케스트레이션·그래프 DB는 합쳐 10% 미만입니다. (2) 동시성(K)을 올리면 처리량은 3배까지 늘지만 요청당 지연이 그만큼 늘고, 에이전트의 행동(funnel)은 전혀 바뀌지 않습니다. (3) 질문 난이도는 "검색이 되는가"가 아니라 "결과를 답으로 마무리하는가"에 작용합니다. (4) 에이전트에게 무엇을 주느냐가 답을 바꿉니다: SEOCHO 스키마 슬라이스 하나로 GRBench 정답이 7/16/3 → 20/29/7(난이도별, N=30)이 되었고, 같은 크기의 엉뚱한 컨텍스트는 0/2/1로 무너뜨렸습니다. 아직 모르는 것은 SPARQL 레인이 왜 어떤 컨텍스트에도 반응하지 않는지, 그리고 hard 문제의 마무리를 어떻게 살리는지입니다.

1 · 실험 장치와 용어

GRBench
Graph-CoT 벤치마크의 MAPLE/Physics 그래프. 논문·저자·학회 노드 276만 개, 관계 6,734만 개. 우리는 DozerDB(Neo4j 호환)에 통째로 넣고 에이전트가 Cypher로 질의합니다. 질문 140개 중 90개를 사용.
GTSQA
Wikidata 부분그래프 위의 질의응답 벤치마크. 케이스마다 자기 그래프(수천~2만 트리플)가 따로 있고 에이전트가 SPARQL로 질의합니다(Oxigraph, 프로세스 내). 1,622개 중 90개 사용.
lane
벤치마크 × 에이전트 구조의 조합. single은 한 에이전트가 ReAct 루프로 스키마 확인·질의·답변을 모두 수행, multi는 manager가 query specialist에게 handoff하는 2-에이전트 구조. 09-12부터 새 실험은 single 두 lane만 다룹니다.
strata-v2, L1/L2/L3
질문 난이도. gold 질의의 구조(hop 수, anchor 수, 패턴 수, 집계, 값 필터, argmax)만으로 점수를 매겨 easy/medium/hard로 나눕니다. 에이전트가 어떻게 행동했는지는 절대 반영하지 않습니다. 층별·lane별 30건씩 동결(strata-v1은 10건).
arm
에이전트가 inspect_graph_schema를 호출했을 때 돌려주는 컨텍스트의 종류. B0 = 그래프가 반환하는 구조(GRBench 62토큰, GTSQA ≈ 990). S1 = B0 + 어휘(node_type/relation_name 값, RDF는 관계 facet)(160 / 1,787). C- = S1과 정확히 같은 크기의 무관한 컨텍스트(대조군). S4 = S1 컨텍스트 + SEOCHO Oxigraph 실행 경로(GTSQA만; 컨텍스트는 S1과 동일). O1 = S1 + 관계 의미(방향·domain/range·속성 역할), 2026-09-12 구현, 미실행.
K (concurrency)
한 vLLM 엔진에 동시에 붙는 에이전트 수. 4/8/16/32를 돌렸습니다.
funnel
케이스 한 건이 답까지 가는 단계별 통과 수(30건 중). triggered 그래프 도구를 쓰기로 함 → validated 질의가 정책 검증 통과 → executed DB에서 실행 → non-empty 결과 행이 있음 → answered 근거 있는 최종 답. budget-exhausted는 6 turn 또는 토큰 예산을 다 쓴 경우.
4계층
케이스 wall time을 나눈 것. GPU decode(토큰 생성), GPU prefill(프롬프트 읽기), Host(vLLM 큐·미분류·클라이언트-서버 차), Graph DB(도구 호출 지연), Agent 잔여(파싱·직렬화·프롬프트 조립).
receipt / trace
모든 실행이 남기는 내용 없는 기록. 프롬프트·답·근거는 *.private.*에만 있고 분석 표에는 시간·토큰 수·결과 코드만 들어갑니다. OTel span 트리(case > chat > tool > DB)가 vLLM 서버 span과 traceparent로 99% 조인됩니다.

3.5 DB 꼬리는 잡혔고, 대신 다음 병목이 보인다 K ≥ 16

수정 전(lab-s3/5/7) GRBench single은 43–63초짜리 label scan 몇 개가 DB 시간의 60–70%를 차지했습니다. 인덱스·15초 트랜잭션 타임아웃·anchor guard를 넣은 뒤(lab-s11) DB 비중은 0.74 → 0.005–0.05, 호출 p90 35 ms입니다. 그런데 K=16/32에서는 타임아웃 도달이 pass당 3 → 9건으로 늘고 p90이 99 ms까지 올라갑니다. 16–32개 에이전트가 하나의 DozerDB를 공유하면 DB가 두 번째 공유 자원으로 드러납니다. anchor guard는 스캔을 즉시 거절하지만 그 뒤 수정된 질의가 row를 얻는 경우는 9–12건 중 1–3건뿐입니다.

4 · 확실하지 않은 것, 그리고 우리가 틀렸던 것

GTSQA(SPARQL)는 왜 어떤 컨텍스트에도 반응하지 않나 미해결

B0/S1/S4/C- 모두 answered 0, 예산 소진 22–29/30. 검증은 되고 non-empty도 10–17건인데 답으로 마무리하지 못합니다. 두 가설: (a) SPARQL ReAct 프롬프트의 마무리 규칙이 없음, (b) "reasoning 토큰 18–20k"로 잡히는 출력이 사실은 도구 호출 인자여서 예산 계산이 왜곡됨(attribution 확인 필요). 이 lane은 스키마가 아니라 루프 자체를 봐야 합니다.

hard의 마무리 미해결

S1을 줘도 L3는 22/30이 row를 쥔 채 예산을 다 씁니다. argmax·연도 필터·closest collaborator류는 결과를 받고도 "이게 답이다"로 넘어가지 못합니다. 후보 레버는 finalisation 규칙(결과가 있으면 다음 turn에 답을 강제)과 turn 예산 조정이며, 아직 실험하지 않았습니다.

vLLM host의 3코어는 포화인가 폴링인가 확인 필요

K와 무관하게 3.0코어로 고정된 host CPU는 "일이 안 늘어서"일 수도, "3개 스레드가 각각 100%로 포화"일 수도 있습니다. 프로세스별(API server / engine core / worker) 분해가 있어야 답이 납니다(011 항목).

우리가 틀렸던 것들

  • multi-agent를 계속 끌고 감: 두 세션 연속 모든 셀 non-empty 0, 5× wall, 6× 토큰. 09-12에 새 실험에서 제외.
  • S4를 ontology arm이라 불렀음: 컨텍스트는 S1과 같고 실행 경로만 달랐습니다. 진짜 ontology 셀(O1)은 이제 만들었고 미실행.
  • speculative decoding 속도만 봄: decode는 빨라졌지만 greedy 질의가 바뀌어 검증률이 반토막. 정확도와 함께 보지 않으면 발표에서 역효과.
  • 인프라 사고들: V13 방치($14), lab-s9의 순서 버그($2.6), lab-s12/13에서 exit code·export 누락. 모두 수정되었고 각각 테스트가 붙었습니다.

5 · 발표 스토리로 엮으면

  1. 계측부터: 요청·turn 단위 3계층 trace(task / GraphCoT / system)를 trace id로 묶었다. 프롬프트·답은 기록하지 않고도 모든 표가 나온다.
  2. 어디가 느린가: decode 82–98%. CPU·오케스트레이션·DB 합쳐 10% 미만. "이질적 파이프라인" 서사는 이 스택에선 성립하지 않는다.
  3. 서빙 레버: TP=2 모놀리스, K는 처리량–지연 교환. speculative decoding은 정확도 parity를 통과해야만 쓸 수 있다(우리 것은 실패). LMCache는 이 모델에 불가.
  4. 난이도: 검색이 아니라 마무리의 문제. 쉬운 질문은 검색을 건너뛴다.
  5. 컨텍스트가 답을 바꾼다: 스키마 슬라이스 하나로 정답 3배, 무관 컨텍스트로 0 — 대조군이 있어서 주장이 선다. 다음은 관계 의미(O1)가 그 위에 얹히는가.
  6. 더 많은 에이전트가 아니라 더 적응적인 실행: multi-agent 수치가 그 근거.
